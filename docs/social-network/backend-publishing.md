# Audience-aware publishing — SN-B15

Implementation on `asmyrogl/B15`, based on B14 commit `56b8123` (merged A10/A11 main is already included). The [owner-approved content contract](content-contract.md) and [Phase 3 data plan](phase-3-data-plan.md) control these changes. This record applies to the working tree, not an untested later revision.

## Delivered boundary

B15 owns post migration, feed/detail/mine/latest-draft reads, author publishing/draft mutations, selected grants and parent-based media access. B16 owns the remaining discussion, reaction, profile/private activity, category/navigation and notification contracts. No Vue publishing UI, group/event/chat policy, new service or deployment is introduced.

[Publishing repository](../../internal/db/publishing.go) takes SQLite's existing social write lock before current ownership, version, category, selection and publication validation. The [HTTP adapter](../../internal/handlers/publishing.go) supports strict 64 KiB JSON and B13 multipart/image limits, presence-aware partial edits, Unicode text limits, optional/null titles, optional categories and incomplete/multiple drafts. It returns full owner post responses, mandatory version conflicts, empty 204 deletions/draft updates, and explicit `data:null` when no latest draft exists. Historical forum fixtures retain their separate adapters.

[Shared permission](../../internal/db/content_access.go) combines active viewer/author, profile restriction, publication and audience in one predicate. Owner detail/drafts/archive remain readable. Feed filtering and totals share one snapshot, with newest-created ordering, Following and category intersection. Selections appear only in owner post responses. New followers see older followers posts; profile privacy never broadens a restricted audience.

Selected grants store exact accepted follow IDs, resolved from submitted account IDs under the same write lock. Constraint triggers reject wrong-author, pending, inactive-participant and nonselected grants and prevent reassignment of an existing granted identity. A before-delete follow trigger advances each affected post version once; FK cascade prunes grants in the same transaction as B12 notice reconciliation. Overflow aborts the transition. Refollow allocates a new identity and restores no selection; author must explicitly reselect it.

Effective post/category/audience/selection/media/status changes advance version and updated_at once, then send the existing empty global invalidation after commit. A no-op verifies access/version, returns the current snapshot and emits nothing. Publishing revalidates current selections and text or ready media. Unpublish/republish preserves IDs, created_at, discussions, reactions and attachments; deleting a post cascades descendants and calls B13's all-owner cleanup after commit. Failed replacements discard only fresh staging and preserve prior content/bytes. JSON cannot claim another resource, pending upload or remote URL.

## Migration and recovery

[Migration 5](../../internal/db/migrations/sqlite/000005_content_audiences.up.sql) rebuilds posts with nullable title, draft completeness, explicit public/version-1 backfills and feed indexes; adds comment version 1 through ALTER rather than rebuilding comments; and adds selected-follow storage/constraints. Old numbered migrations are unchanged.

The [startup driver adapter](../../internal/db/content_migration.go) recognizes this migration's explicit marker; other files keep the original transactional driver. Before serving any application request or sweeping media, the rebuild pins one migration connection, disables/asserts FK enforcement before starting its transaction, captures original posts indexes/triggers and the historical AUTOINCREMENT sequence, copies every original post column, and checks bidirectional EXCEPT before dropping the source. It recreates the original-named table and saved schema objects, restores sequence allocation and runs `foreign_key_check` before commit. Foreign keys are restored/asserted on that connection even on error/cancellation. The normal DSN still enables them for every application connection.

Failures roll back the rebuild and retain migration 5's dirty marker; subsequent startup refuses readiness. No automatic version forcing or destructive retry occurs. Migration 5 down deliberately refuses lossy removal. Before upgrading, stop writers and back up consistent SQLite, complete private MEDIA_ROOT and actual legacy source mounts. Recover through the existing [migration guide](backend-migrations.md) and [B13 media recovery](backend-content-media.md#upgrade-and-recovery-handoff) using coordinated backups and the matching runtime.
