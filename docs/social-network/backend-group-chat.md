## Delivered behavior

- **Migration 10** ([up](../../internal/db/migrations/sqlite/000010_group_chat.up.sql), [down](../../internal/db/migrations/sqlite/000010_group_chat.down.sql)) is additive: `group_messages` (sender, historical sender membership ID, retry nonce unique per sender across rooms, body 1–2000 characters, index `(group_id,id)`) and `group_read_cursors` keyed by membership with `ON DELETE CASCADE`, so departure removes the cursor and nothing else. Triggers keep cursors monotonic and start a cursor at the room's latest message on **every** membership insert, including the creator row written with a new group, so admission, readmission and the migration itself need no hand-written hook and a lazy first fetch can never skip an intervening message. Nothing existing is rebuilt: messages, notices, media, sessions and sequences are untouched. One room exists per group by construction (its messages carry the group ID), so groups from earlier phases need no backfill row.
- **One membership decision.** Every route checks the viewer's current active membership in a group whose creator is still active (the rule shared with events). An outsider, invitee, requester, departed or removed member gets `404 Not found` before anything else, including for their own retained messages; a current member holding an old membership ID gets `409 STALE_MEMBERSHIP`. Field validation precedes the permission check, as in the contract.
- **Send** is one command shared by `POST /groups/{id}/messages` and the socket's `group.send`. A required lowercase UUID v4 `client_id` is unique per sender: an exact retry returns the original message (HTTP 200, `chat.ack` with `duplicate:true`) with no new row and no fanout, including after restart; a changed body, another room or another membership generation is `409 MESSAGE_CONFLICT`. Permission and generation are rechecked before the retry lookup, so a departed member cannot replay a stored result. Bodies are LF-normalized, edge-trimmed, 1–2000 code points, no controls besides tab and line feed; the body is text only and an `image_url` key is rejected as an unknown field.
- **Read model.** `GET /groups/{id}/messages` pages by `before_id`/`limit` (default 10, maximum 50), ascending within the page, with `next_before_id`, and shares its query parser with direct messages. `GET /group-chats` lists the viewer's current rooms by group ID, empty rooms included, with `membership_id`, the last message, `read_through_id` and `unread_count`; `GET /group-chats/unread` counts across current rooms only, independent of paging. Unread excludes the viewer's own sends. A private-profile author exposes only `sender_id` and the display name; an inactive author is shown as `Unavailable account`.
- **Cursors.** `PUT /groups/{id}/messages/read` advances the cursor of the caller's current membership. Zero and older IDs are no-ops, an ID that is not in this room (another room, a direct message, a future ID) is `400 through_id: INVALID_ID`, and `chat.read` goes to the reader's own sessions only when the cursor moved. Fetching history, receiving a frame and sending never mark read, and message counts and notification counts never affect each other. A new member starts at the room's latest message: the whole history is readable and nothing is counted as backlog.
- **Fanout.** Each committed message is delivered once to every session of every member in the commit-time snapshot, the sender included; an exact retry fans nothing out. A socket send is acknowledged on the requesting socket first (the ack shares the sender's queue with its own copy, so it precedes it); an HTTP send has no ack. Session buffers keep the existing bounded, non-blocking behavior: a full buffer drops the frame and the client recovers by refetching.

## Delivery authorization through the socket write

A queued room frame is re-authorized when it is written, against the **exact membership generation** it was queued for:

- Each recipient's `group.message`, `chat.ack` and `chat.read` is built with `handlers.GroupFrame`, which stamps the recipient's membership ID into an internal envelope key. `authorizeFrame` checks `GroupDeliveryAllowed` (that very membership still belongs to that viewer in that group, in a visible group) and removes the key before writing, so it never reaches a client. A frame without a generation cannot be authorized and is suppressed. A frame queued before a departure is therefore never delivered after it, even to a member who has since returned under a new membership ID.
- The check and the write share the B22 admission: `Hub.WithDeliveryAdmission` holds the shared gate through both, and the leave/removal handler (`DELETE /group-memberships/{id}`, the only write that ends a member's access) takes `Hub.WithRevocation` around just its database write. A frame authorized earlier is written before the departure can commit; a frame written afterwards is re-evaluated and suppressed. Lock order stays session gate → delivery gate → SQLite, and a stalled peer holds the gate for at most one 10-second write, never a SQLite transaction.
- A message committed before the departure stays stored even if its delivery is suppressed. Re-evaluation at the write replaces a buffer purge: a suppressed frame is dropped, never replayed, and nothing queued before a removal is delivered after readmission. If authorization itself fails (a busy database), that frame is suppressed and logged and the connection stays open.
- `chat.error` carries no private data and is delivered to the requesting socket only; an error never discloses group or message details.

Socket framing is the strict B22 schema extended by one command: the envelope may only be `{type, payload}`, `dm.send` and `group.send` are the only client commands, payloads reject unknown keys and wrong types, and frames over 16 KiB close with 1009. Field problems are `VALIDATION_ERROR` with `fields`; `client_id` is echoed only when it is a valid nonce.

## Choices the contract left open

- `group_messages.client_id` is nullable, with a length-36 check, where the data plan says `NOT NULL`: the approved fixtures seed pre-nonce history as `client_id: null` and expect it back verbatim. Every writer supplies a UUID, and a null can never match a retry.
- The internal generation key travels in the queued frame's envelope rather than in the payload, because the approved `GroupMessage`, `chat.ack` and `chat.read` shapes have no generation field and the delivery fixtures require a returned member's old frames to stay suppressed.
- `GroupsHandler` now receives the hub so the departure write can be ordered against queued frames; with no hub (tests without sockets) it runs unordered.
- Migration 10's down script refuses when any message exists or any cursor is not 0 (the value migration and the empty-room admission give it), so an untouched upgrade downgrades and re-upgrades to identical cursors, and any stored message is treated as data.
- A room whose creator account is inactive is hidden from every member, matching the event and group visibility rule.

## Handoff

SN-A20 consumes the approved `GroupMessage`, room and cursor DTOs, `client_id` nonces, `membership_id` on every write, `group.message`/`chat.ack`/`chat.read`/`chat.error` frames and the refetch-on-reconnect rule; when a send's outcome is uncertain it refetches history or retries the same payload with the same nonce, never a new one, and never re-submits automatically after `STALE_MEMBERSHIP`. B23 changes no shared runtime or CI file; the harness needs no new setting because the room uses the existing socket, database and migration runner.
