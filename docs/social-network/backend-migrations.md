# Backend startup migrations — SN-B03

Production startup opens `DB_PATH` (default `./data/forum.db`) with SQLite foreign keys and a five-second busy timeout. It refuses an unversioned database containing application tables. Select a **new database path** for social-network; back up any forum database first. Startup never deletes or upgrades forum records. Empty databases receive the embedded numbered SQL files from `internal/db/migrations/sqlite/` before category bootstrap and before HTTP starts. Repeated startup applies no duplicate schema or seed data. The old `forum_schema.sql` and procedural `Migrate` remain for inherited forum test fixtures; neither runs in `InitDB`.

The first migration creates account fields required by the approved [storage decision](data-decision.md): birthdate, nullable nickname/about-me/avatar key, case-insensitive unique email, and compatibility columns used by retained code. Session rows allow independent tokens and an optional revocation timestamp. The old 12-hour session behavior is still in Go and belongs to SN-B05; request validation and account writes belong to SN-B04. QA seeds have explicit synthetic birthdates and run only through `make seed-qa`, never normal startup.

If a migration fails, startup returns an error and does not listen. The failed version remains marked dirty in `schema_migrations`; restart does not auto-repair it. Restore a known-good backup, or inspect the failed SQL and database, repair explicitly, then clear the recorded dirty state with migration tooling before restarting. Do not delete the database or force a version without verifying the schema. Keep database and media backups together once avatar storage is added in SN-B09.
