## Delivered behavior

- **Migration 9** ([up](../../internal/db/migrations/sqlite/000009_dm_cursors.up.sql), [down](../../internal/db/migrations/sqlite/000009_dm_cursors.down.sql)) is additive: a nullable `private_messages.client_id`, a partial unique index `(sender_id, client_id)`, the two pair indexes `(sender_id, recipient_id, id)` and `(recipient_id, sender_id, id)`, the persisted `dm_read_cursors` table and a safe-integer guard on new message IDs. Every existing message, ID, body, image reference, media link and staged object is untouched. Each existing pair's cursor is bootstrapped in both directions to the pair's latest message, so legacy browser-only unread state is not invented as a server backlog. A new messageable pair starts at 0 and cursors are inserted lazily before the first send or read.
- **One permission predicate.** `can_send` is distinct active participants plus an accepted follow in either direction; pending requests never qualify. It is checked inside the serialized `BeginSocialWrite` transaction by send, by the staging upload and by the retry lookup, so an unfollow either precedes a send (404, nothing stored or claimed) or follows it (the message stays). An exact retry after revocation is also denied. History, roster rows, counts and committed media stay participant-only after both users unfollow.
- **Send** is one command shared by `POST /chats/{id}/messages` and the socket's `dm.send`. A required lowercase UUID v4 `client_id` is unique per sender: an exact retry returns the original message (HTTP 200, `chat.ack` with `duplicate:true`) with no new row, image claim or fanout, including after restart; a changed body, recipient or image is `409 MESSAGE_CONFLICT`. Bodies are LF-normalized, edge-trimmed, at most 2000 code points, no controls besides tab and line feed; empty text needs an image. Stored legacy bodies are never trimmed, truncated or revalidated.
- **Offline storage and live delivery.** A message is stored whether or not the recipient is online. The sender's sessions always receive the committed `dm.message` echo; the recipient's sessions receive it whenever they hold a socket and the pair may still message (amended 2026-10-29, pending owner approval; the original rule withheld it unless the recipient followed the sender or was public). Reconnect, focus and the 60-second recovery refetch stored data for sessions that were offline. Nothing is replayed over a socket.
- **Read model.** `GET /chats` lists existing conversations (latest message first) then messageable people with no history (normalized display name, then ID), with `can_send`, `unread_count`, `read_through_id` and a 200-code-point preview (`[image]` for image-only). `is_online` appears only when the viewer may see that profile (decided in the same snapshot as the rest of the row). `GET /chats/{id}/messages` pages by `before_id`/`limit` (default 10, maximum 50), ascending within the page, with `next_before_id`. `GET /chats/unread` counts across all conversations independent of paging. `PUT /chats/{id}/read` advances a persisted, monotonic cursor, rejects an ID outside the pair (`through_id: INVALID_ID`), treats 0 and older IDs as no-ops and emits `chat.read` to the reader's own sessions only when the cursor moved. Message counts and notification counts never affect each other.
- **Images.** `POST /chats/{id}/images` requires current `can_send`, exactly one `image` part (any other part is 400, a non-multipart type 415) and the existing JPEG/PNG/GIF bounds; staged bytes are readable only by the uploader. A send claims the object once; a denied send leaves it staged; a claimed object cannot back another message. Committed bytes remain participant-only after unfollow, restart and cleanup sweeps.

## Delivery authorization through the socket write

Every queued private frame is re-authorized when it is written, under one admission that spans the check and the write:

- `Hub.WithDeliveryAdmission` holds a shared gate while the socket writer rechecks the session, presence visibility, the `dm.message` recipient predicate or `chat.read` conversation access, and then writes. The write deadline starts only after the gates are held, so a stalled peer holds the gate for at most one 10-second write and never holds a SQLite transaction.
- `Hub.WithRevocation` takes the same gate exclusively. The follow-removal and privacy-change handlers — the only HTTP writes that can end a recipient's permission, since follow creation and request decisions only grant or cancel pending state — hold it around just their database write, after the session admission and before any SQLite work, never while the request is read or answered. A revocation therefore waits for in-flight writes; a frame authorized earlier is written before the unfollow can commit, and a frame written afterwards is re-evaluated and suppressed. Lock order is session gate → delivery gate → SQLite.
- If re-authorization itself fails (for example a busy database), that frame is suppressed and logged and the connection stays open; clients recover by refetching.
- A message committed before revocation stays stored even if its delivery is suppressed. Re-evaluation at the write replaces a buffer purge for DM frames: a suppressed frame is dropped, never replayed, and a frame still queued when the relationship is restored is judged against the restored state like any other. B23 reuses the gate for membership generations.

Socket framing in the social schema is strict: the envelope may only be `{type, payload}`, a frame other than a valid `dm.send` is `chat.error INVALID_PAYLOAD`, payloads reject unknown keys and wrong types, and the frame limit is 16 KiB (larger frames close with 1009 and change no state). Field problems are `VALIDATION_ERROR` with `fields`; `client_id` is echoed only when it is a valid nonce. A legacy send without `client_id` fails validation. The inherited forum-schema socket path used by legacy fixtures is unchanged.

## Choices the contract left open

- A syntactically invalid `image_url` (not a private media reference) is `400 VALIDATION_ERROR` with `image_url: INVALID_ID`; a well-formed reference that is unknown, someone else's or already claimed is `404 Not found`.
- New message IDs above 9007199254740991 abort the insert (trigger), so an overflow cannot leave a message, cursor or media claim behind.
- Migration 9's down script refuses when any message carries a nonce or any cursor differs from the pair's current latest message (its bootstrap value); an unchanged bootstrap-only state downgrades and re-upgrades identically. QA reset removes cursors before users.
- Messages sent by or to an inactive account stay stored; the conversation disappears from the counterpart's roster, counts and history.
