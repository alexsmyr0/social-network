## Session and origin behavior

- Session rows live in SQLite with token, `expires_at`, `is_valid`, IP, and user agent ([schema](../../internal/db/forum_schema.sql#L101-L111)). Login/register invalidate previous sessions for the user, then issue one new token with **12-hour expiry** ([sessions](../../internal/db/sessions.go#L13-L16), [CreateSession](../../internal/db/sessions.go#L39-L95)). Protected HTTP routes look up the cookie token and reject expired/invalid rows ([auth middleware](../../internal/middleware/auth.go#L19-L44), [query](../../internal/db/sessions.go#L179-L235)). This conflicts with staying signed in until logout; SN-B02 must approve persistence and concurrent-session policy, then SN-B05 implements it.
- Issued cookie is `HttpOnly`, `SameSite=Lax`, `Path=/`, with `Secure` selected from `FRONTEND_URL`; it has **no `Expires` or `Max-Age`**, so it is a browser-session cookie ([cookie helper](../../internal/handlers/users_helpers.go#L16-L48)). Browser restart persistence is therefore unproven and cannot be assumed from the database row. SN-B02/B05 need a cookie and server policy plus a browser-reopen test in SN-A07.
- Cleanup compares RFC3339 `expires_at` text (`T` separator) with SQLite `datetime('now')` text (space separator) ([cleanup](../../internal/db/session_cleanup.go#L10-L23)); a disposable SQLite comparison of a same-day one-hour-old timestamp returned false. Auth still rejects expired sessions using a matching RFC3339 comparison ([valid-session query](../../internal/db/sessions.go#L179-L200)), but cleanup can retain expired rows until a later date. SN-B05 should align timestamp formats and add a same-day expiry cleanup case; the existing test uses years 2000/2999 ([test](../../internal/tests/session_lifecycle_test.go#L64-L112)).
- The frontend serves same-origin `/api/` and `/ws` through a reverse proxy to hardcoded `http://localhost:8080` ([frontend routes](../../cmd/frontend/routes.go#L74-L90)); the backend defaults `FRONTEND_URL` to `http://localhost:3000` for CORS ([router](../../internal/router/router.go#L28-L36), [CORS](../../internal/middleware/middleware.go#L79-L95)). WebSocket upgrade checks cookie and origin separately ([WS handler](../../internal/handlers/ws.go#L29-L57), [upgrade](../../internal/handlers/ws.go#L76-L103)). CORS headers alone do not enforce an HTTP write-origin/CSRF policy; SN-B02 should define one. SN-A02 must approve the browser/runtime origin boundary before the final auth contract.

## Migrations, existing databases, and fixtures

- `InitDB` opens SQLite with foreign keys, WAL and a busy timeout, executes embedded `forum_schema.sql`, calls `Migrate`, then seeds default categories ([startup](../../internal/db/db.go#L20-L93)). Backend startup calls it before serving requests ([server](../../cmd/backend/server.go#L19-L75)). The schema uses `CREATE TABLE IF NOT EXISTS`; `Migrate` uses Go-coded column checks, table rebuild and email normalization in one transaction ([migration](../../internal/db/migrate.go#L12-L131)). There are **no numbered migration files, version table, or migration library**. Thus startup is not the procedural, file-organized migration flow requested by [the assignment](requirements.md#migrate). SN-B08 selects policy/library/layout; SN-B03 implements and tests it.
- Existing-account preservation is partly supported: migration tests cover adding profile columns, retaining rows and rerunning ([fixture](../../internal/tests/migrate_test.go#L26-L45), [tests](../../internal/tests/migrate_test.go#L94-L150)). Case-folding migration leaves pre-existing duplicate emails unresolved and skips the unique index while allowing startup ([migration](../../internal/db/migrate.go#L200-L253), [test](../../internal/db/migrate_email_case_test.go#L98-L123)). Old databases may also have `age=0` and empty names/gender from earlier migrations. SN-B08 must choose **preserve/upgrade versus explicit fresh start**, define recovery for invalid legacy rows and duplicate emails, and decide the dependency (`golang-migrate`, another allowed migration package, or an agreed in-house runner). No production-data policy is inferred here.
- QA reset/seeding is a separate `cmd/qa-seed` command, not normal startup ([command](../../cmd/qa-seed/main.go#L15-L42), [seed runner](../../internal/db/db.go#L96-L133)). Its users fixture supplies usernames, ages and genders but no birthdates or optional fields ([fixture](../../internal/db/seeds/10_users.sql#L1-L21)). `internal/tests/helpers_test.go` and other tests build `CreateUserRequest` with legacy fields ([shared test helper](../../internal/tests/helpers_test.go#L22-L62)). SN-B03/B04 must update disposable fixtures without inventing birthdates for existing people.

## Media, packaging, and caller impact

- Post/comment and DM uploads accept multipart field `image`, cap total request body at **20 MiB**, and detect JPEG/PNG/GIF from bytes ([multipart limit](../../internal/handlers/posts_helpers.go#L160-L179), [type check](../../internal/handlers/posts_helpers.go#L181-L237)). Files are written relative to the backend working directory under `web/static/uploads/`, with DM images under `dm/` ([writer](../../internal/handlers/posts_helpers.go#L239-L285), [DM endpoint](../../internal/handlers/chats.go#L106-L146)). This code is a reuse candidate for avatars, subject to an approved ownership/access and failure-cleanup design in SN-B02/B08/B09.
- The frontend, rather than backend, serves `/static/` from its own `./web/static` path ([frontend routes](../../cmd/frontend/routes.go#L46-L55)). The existing [Dockerfile](../../Dockerfile#L6-L47) builds **only the backend executable**, copies no upload/static tree, and gives its non-root user `/data` for SQLite; [Makefile Docker targets](../../Makefile#L168-L189) start one backend image. The separate-image requirement needs an upload delivery/storage choice in SN-A02/B08 and backend/frontend image work in SN-B06/SN-A06. Current relative upload path cannot be assumed to work in the existing backend image.
- Changing required `username` affects SQL joins/serializers for posts, comments, notifications and chat, plus the WebSocket sender label ([examples](../../internal/db/posts.go#L95-L103), [notifications](../../internal/db/notifications_queries.go#L30-L62), [chat roster](../../internal/db/messages.go#L102-L151), [WS cache](../../internal/handlers/ws.go#L99-L104)). The SPA registration payload sends username/age/gender and lacks DOB/optional fields ([payload builder](../../SPA/features/auth/auth.handlers.js#L109-L126)); profile and chat render username ([profile](../../SPA/features/profile/profile.views.js#L31-L52), [chat roster](../../SPA/features/chat/chat.roster.views.js#L40-L76)). Optional nickname needs an explicit display fallback that works when absent and keeps stable IDs intact; this is a SN-B02 contract decision, not an implicit rename.
