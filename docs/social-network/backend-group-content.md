# Group content and membership enforcement — SN-B19

Implementation on `asmyrogl/B19`, branched from merged main `4bde9d0` (B18 and A15 included). The [owner-approved groups contract](groups-contract.md#group-content-extension), [Phase 4 data plan](phase-4-data-plan.md) and [fixture pack](fixtures/phase-4-contract.json) control these changes; [Phase 4 decisions](phase-4-decisions.md#group-content-and-existing-features) are not reopened. This record covers the working tree, not an untested later revision.

## Delivered boundary

B19 adds an optional, immutable group scope to existing posts and makes **current membership** the one decision for every group-content surface. Personal posts keep their profile/audience rules unchanged. No Vue code, group chat, events, moderator role, ownership transfer, group deletion, personal-to-group conversion, new queue, socket, database or service is introduced.

| Concern | Implementation |
|---|---|
| [Migration 000007](../../internal/db/migrations/sqlite/000007_group_posts.up.sql) | `ALTER TABLE posts ADD COLUMN group_id … REFERENCES groups(id) ON DELETE RESTRICT` (no table rebuild, so no foreign-key disabling), partial index `idx_posts_group_feed`, and three triggers: a group post must be inserted by a current active member and store the inert audience `public`; `group_id` can never change; the audience of a group post can never leave `public`. Every existing post keeps its ID, author, status, audience, version, times, categories, attachments, selections, and a `NULL` group. |
| [Shared decision](../../internal/db/content_access.go) | `contentPermission` is `CASE WHEN p.group_id IS NULL THEN <personal rules> ELSE <active viewer, active author, current membership, published or own draft> END`. Detail, thread, comment detail, reactions, activity, categories, navigation, profile lists, media and notices all reuse it, so the two rule sets are never OR-ed and a follow, a public profile or a stored audience cannot widen group access. |
| [Publishing](../../internal/db/publishing.go) | `WritePublishingPost` takes the create-only `GroupID`: membership is checked under the social write lock (a removal either commits first and the create is `404`, or after it and the post is retained); `audience`/`selected_follower_ids` with a group, or on a group post, are `GROUP_SCOPE`; `group_id` on `PATCH`/`PUT` is `IMMUTABLE`. Edit, delete, publish/unpublish and draft changes need current membership through `requirePostAccess`. |
| [Reads](../../internal/db/content_reads.go) | Post and draft projections carry `group:{id,title}|null`; group posts report `audience:"group"` and never `selected_follower_ids`. `GET /posts?group_id=`, `GET /posts/{id}/nav?group_id=` and `GET /posts/draft?group_id=` require membership in the same read snapshot as the page (`404` otherwise). The home feed is the personal rule set plus member groups' published posts, filtered before counting and paging. `GET /posts/draft` without `group_id` returns personal drafts only. |
| [Notices](../../internal/db/content_access.go) | `canReceiveContentNotice`: no comment/like/dislike notice is inserted for a recipient who is not a current member of the post's group. Listing, counting, unread, read-one and read-all already evaluate `contentPermission` with the recipient, so hidden stored notices keep their read state and reappear after fresh admission. Group invitation/request notices stay always listable. |
| [Handlers](../../internal/handlers/publishing.go) | `group_id` parsing (JSON number or multipart decimal; `0` is `INVALID_ID`, a string is `400 BAD_REQUEST`), strict query keys, an early membership guard before any upload is staged. |
| Realtime | Content changes keep the existing all-authenticated `social.invalidate`; membership transitions (B18) already invalidate the affected users and current members. Refused writes send nothing. |
| [QA reset](../../internal/db/seeds/00_reset.sql) | Already deletes posts before groups, so the `RESTRICT` reference never blocks a reset. |

## Behavior notes beyond the contract text

- **Profile comments on group posts carry the parent projection.** The pack's `profile-comments-departed-visible-to-member` case expects `GET /users/{id}/comments` items for a group post to include the activity-style `post` projection with `group`. Phase 3's `profile-comments` case expects none for personal posts, so the projection is attached **only when the parent is a group post**; personal-post comments keep the Phase 3 shape exactly. The phase 3 fixture tests ignore the additive `group:null` key on posts and drafts, which Phase 4 adds to the wire shape.
- **Canonical media IDs only.** `/api/v1/media/01` used to alias `/api/v1/media/1` for authorized readers. The contract says aliases stay `404`, so a leading zero is no longer a media URL. This is a hardening of B13's parser; it never allowed a bypass of authorization.
- **Departed authors keep stored contributions, lose every path.** Their posts, comments, reactions and attachments remain stored and visible to current members with the author's display name; the author reads and writes nothing (including their own drafts, activity, media and direct links) until a fresh admission.
- **Group creator inactive.** Matching B18, discovery hides such a group; members' content access follows the data-plan predicate exactly and is unchanged by the creator's state.
- **Down migration.** `000007` down refuses while any group post exists and otherwise removes the objects and column; the B18 down migration must run after it.

## Upgrade and recovery

A version-6 database gains `posts.group_id` (all `NULL`), the index and the triggers without rewriting any row; IDs, `sqlite_sequence`, categories, selections, comments, reactions, notices and media associations are unchanged and `foreign_key_check` is clean. A failed migration leaves schema and data unchanged, marks version 7 dirty and blocks readiness until repaired; the normal connection keeps foreign keys on. Back up the SQLite file and `MEDIA_ROOT` first, as the [migration guide](backend-migrations.md) requires. Private bytes of departed authors stay referenced by their retained posts and comments, so the post-commit sweeper and restart reconciliation never delete them.
