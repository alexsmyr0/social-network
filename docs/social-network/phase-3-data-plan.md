## Atomic transitions and version semantics

Reuse `BeginSocialWrite` and shared profile/post predicates. Reads use one snapshot; writes lock before permission/version/follower validation. No prior handler check is authority. Profile AND audience AND status checks must compose before counting/paging in every B15/B16 consumer, including attachments and notices. Public account does not imply public-audience-only visibility, and full-profile access never bypasses selected audience.

Within a single owner post edit transaction: authenticate current active author, compare version, calculate merged fields, resolve eligibility, stage/check owned durable media, replace category/selection associations and post fields, increment version once if effective change, commit, then invalidate/sweep. Switching selected→public/followers removes grants before commit. Publishing a selected draft validates current accepted identities and nonempty grants; invalid input fails without dropping good prior grants. Reactions/comments remain stored after unpublish or audience restriction. Exact no-op emits nothing and does not advance versions.

Within accepted-follow deletion: identify affected selected posts before deleting follows; prune grants by FK cascade; advance each affected post version/updated_at once; reconcile notices using existing B12 transaction; commit; issue empty invalidation. Version overflow fails whole transaction. Owner updates serialized after removal see no old relationship and cannot reinsert its grant. Updating before removal is safe because removal subsequently deletes that grant. Public/private switches preserve accepted follow IDs or auto-accept pending IDs as approved; they never fabricate selected grants.

Post deletion cascades comments/nested descendants, reactions, category links, notices and post/comment media links. Comment deletion cascades descendants/reactions/notices/media links. Sweep private bytes after commit only if no avatar/post/comment/message/pending owner remains; keep original sources and all unknown legacy assets. Media pending writes and replacement/rollback follow B13: durable file before reference, failed commit discard only fresh request-owned staging, cleanup I/O failure after commit is deferred to restart. No expiry for DM staging is added.

## Rebuild safety and recovery

Relaxing the existing nonempty title CHECK requires a posts rebuild; **do not copy B12's notifications-only drop/rename verbatim**. Incoming FKs reference posts from comments, reactions, notifications, post_categories and media_links. Dropping posts with FK enforcement on can cascade away those records. Renaming old posts can retarget foreign keys and media triggers to the old name. No use of writable_schema or resetting the database is authorized.

B15 must implement and test a maintenance-only rebuild on a dedicated migration connection, while no application writers/cleanup are running. Disable FK enforcement on that connection **before** opening the rebuild transaction; assert disabled. The current SQLite migration driver wraps files in transactions by default, so `PRAGMA foreign_keys=OFF` inside an ordinary migration file is insufficient. Adapt existing migration startup deliberately, with connection-pinned foreign-key handling and explicit transaction ownership for this migration; other migrations retain their guarantees. Do not turn off foreign keys on a live application pool or leave them off after success/failure. This plan specifies requirements, not untested executable SQL.

Copy the old posts and any rebuilt comments into replacement tables with exact IDs/times/fields; verify row counts and bidirectional EXCEPT over every original column before source removal. Preserve `sqlite_sequence` allocation even when highest historical ID was deleted, not only MAX(id). Capture/recreate all relevant indexes and triggers from migrations 000001–000004, especially the media resource image triggers. Use final original names so external FKs still reference `posts`/`comments`; validate schema references, every media link and pending row before commit. Run `foreign_key_check` inside the rebuilt transaction even with enforcement disabled and refuse commit on any row. After commit restore/assert FK enforcement, reopen normally and validate migration/readiness before serving. On exceptions close the dedicated connection; the normal pool must still enforce FKs. A dirty migration version blocks readiness and is not forced clean automatically.

Preserve all unchanged dependent tables and bytes, including historical multi-owner media and pending DMs. Any proposed different rebuild mechanism is acceptable only if it proves the same preservation/atomic/failure invariants; record its implementation evidence under B15. Stop old writers, back up consistent SQLite plus complete private MEDIA_ROOT plus all actual legacy mounts first. On failure restore a coordinated backup or repair the dirty version explicitly using the existing migration guide; never rerun destructive SQL blindly. Down migration must refuse lossy removal once audience/grants/optional-title content exists; use coordinated backup with matching runtime instead. Repeated startup verifies current schema without recreating tables or changing public mappings.
