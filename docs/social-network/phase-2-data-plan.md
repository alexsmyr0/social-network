## Migration sequence and ownership

Current production schema is [migration 000001](../../internal/db/migrations/sqlite/000001_initial.up.sql), applied by [startup migrations](../../internal/db/startup_migrations.go), then category bootstrap and [avatar preparation](../../internal/db/avatar_storage.go). Extend embedded numbered files under `internal/db/migrations/sqlite/`; never change 000001 to upgrade existing installations. Exact next numbers must be checked at implementation time; these reservations assume 000001 remains latest.

| Planned version / owner | Changes and preservation |
|---|---|
| 000002 / B11 | `users.profile_visibility` default `public`, `profile_version` default 1, display-name search key; single `follows` table and indexes. Backfill all active/inactive existing users without changing registration fields, sessions or avatar keys |
| 000003 / B12 | Rebuild notifications to support follow targets while copying IDs, five existing types, actor/recipient/content references, creation time and read flags. Preserve existing content uniqueness indexes; add follow uniqueness. Backfill one notice for every still-pending follow |
| 000004 / B13 | Media reference/ownership manifest and restartable file-copy migration, shared cleanup and authorized compatibility reads. Keep every content/DM reference and recoverable source byte; no post audience or optional-title migration here |

B11 must expose a transaction seam that B12 can extend: create/accept/remove follow and change privacy using the caller's same transaction, with affected participants/removed follow ID collected for post-commit signals. B11 does not insert unsupported notification types before B12's schema exists. B12 extends **all** transition paths and backfills existing pending rows, so no earlier request is missed. The retained `CreateComment` currently commits the comment separately and ignores notification-insert failure; B12 must move comment plus notice insertion into one transaction, retaining current deduplication, and signal only after commit. Reaction paths already use transaction-aware notice hooks and must retain that ordering. A11 requires both deliveries, not B11 alone.

## Fields, constraints and query mappings

| Storage / invariant | API mapping and implementation owner |
|---|---|
| `users.profile_visibility TEXT NOT NULL DEFAULT 'public' CHECK IN ('public','private')` | Profile visibility and shared `CanViewProfile(viewer, subject)` predicate; B11 |
| `users.profile_version INTEGER NOT NULL DEFAULT 1 CHECK >= 1` | Owner-only Profile version; compare-and-increment actual privacy changes atomically; B11 |
| `users.display_name_search TEXT NOT NULL DEFAULT ''` | Unicode-lowercased current nickname/fallback name, backfilled by Go inside the migration handoff before readiness; index `(display_name_search,id)`, literal substring query with escaped LIKE metacharacters and case comparison matching contract; B11 |
| `follows.id INTEGER PRIMARY KEY AUTOINCREMENT` | Never-reused `follow_id`; avoid resetting `sqlite_sequence`; IDs within agreed JSON integer ceiling; B11 |
| `follows.follower_id`, `followed_id` required FKs → users with cascade; unique ordered pair; CHECK unequal | Directional identity/no self-follow; never infer mutual follow; B11 |
| `follows.state` CHECK `pending`/`accepted`; required `created_at`; nullable `accepted_at` with pending→null / accepted→non-null CHECK | Follow payload and transitions; delete on cancel/decline/unfollow; preserve ID on accept/auto-accept; B11 |
| Index `(followed_id,state,created_at,id)` and `(follower_id,state,followed_id)` | Incoming requests, accepted lists, access checks/counts; B11 |
| Notification `follow_id` nullable, `follow_state` nullable | Historical request identity/status after relationship deletion; not a cascading FK to current follows, since history must survive cancel/unfollow; B12 |
| Notification type/target CHECK | Follow type requires follow ID/state and null post/comment; existing content types retain exactly one stored post/comment target and null follow fields. Existing `comment` targets a post; comment reactions target comments; B12 |
| Follow-notice unique `(recipient_id,follow_id)` WHERE follow ID non-null | One notice per request cycle; a retried request has a new ID; B12 |
| Notification read flag, actor/recipient FKs, original IDs/times and content FKs/indexes | Preserve inherited history/read/deduplication, exclude inaccessible rows at query time; B12 |

The search-key backfill cannot use SQLite `lower()` alone for non-ASCII names. Migration 000002 adds the non-null column with empty default; B11 adds a readiness backfill transaction populating every empty key from existing nickname/fallback using Go's Unicode lowercase. New registrations populate it in their account transaction. Repeated startup verifies/reconciles keys before accepting requests; a backfill failure refuses readiness and can safely retry without resetting migration state. No partially searchable directory is served. The substring match may scan the name index; the index is not a promise of accelerated arbitrary substring search. No FTS dependency is chosen here.

Full-profile query projection explicitly lists approved registration fields; it never serializes `db.User` wholesale. Phase 1 [Account](../../internal/db/accounts.go) serializers retain their shape. Shared predicate allows active viewer/subject when owner, subject public, or an accepted viewer→subject pair exists. Pending grants nothing. Collections project each member separately; authorized count/list access concerns the list owner, while member details obey member privacy. Hidden/inactive subjects are excluded before totals. Content predicate in Phase 2 combines active authors/profile permission and publication status, retaining owner draft access; B14/B15 later add audiences.

Transactions must acquire serialization before reading privacy/request state (SQLite write-lock or equivalent transaction with full retry of busy-snapshot failures). Unique constraints are the last line of defense, not a replacement for state checks. Retry a transaction only before response/side effects, and emit signals only from committed results. Privacy auto-accept, request reconciliation, and follow removal occur atomically; SQL errors cannot produce success or premature frames. Future selected-post associations are removed on unfollow when B15 introduces them; Phase 2 must not access nonexistent tables.

## Media ownership and safe upgrade

B13 extends private `MEDIA_ROOT` storage with a durable manifest: media ID, opaque object key, verified MIME/byte count, legacy relative URL if any, migration status (`pending`/`ready`/`missing`), and normalized resource associations. Associations record one concrete owner kind/id: account avatar, post, comment, stored DM, or sender-owned pending DM upload. Do not grant attachment access by caller-provided ID/URL alone. Keep existing `users.avatar_key` values and avatar URLs valid; account avatar entries are backfilled before a shared cleanup sweep runs. Mapping tables/constraint details are internal to B13 and must preserve these invariants.

Personal attachments authorize through their current owning post/comment (comments inherit parent-post privacy, not commenter privacy). DM attachments authorize only existing sender/recipient participants; pending uploads authorize only uploader until attached to the validated recipient's message. Shared bytes with multiple associations are readable only if at least one association is authorized for the viewer, but new cross-owner URL attachment is prohibited. A new upload cannot claim someone else's existing media. Use backend `GET /media/{id}` for new content/DM URLs; compatibility `/static/uploads/...` must proxy to an equivalent checked lookup with no redirect to raw disk. Missing/unauthorized/traversal paths return the same 404 after session checks; anonymous returns 401; disk failures are 5xx without bytes.

Keep JPEG/PNG/GIF and use the existing avatar decoder budgets for new retained-content/DM uploads: 5 MiB per file, 4096 per side, GIF ≤100 frames and ≤64 million cumulative canvas pixels; content-type/extension mismatches or corrupt/unsupported bytes are `422 INVALID_IMAGE`, excessive bytes/body are `413 PAYLOAD_TOO_LARGE`. Multipart body remains at most 10 MiB for retained content compatibility; B14 sets precise content-field budgets later. Existing committed recoverable media is not deleted solely for failing a newly introduced upload budget; report it for controlled recovery and never serve an unsafe type as executable content.

Upgrade order, before readiness and before any orphan deletion:

1. Stop old writers and back up consistent SQLite plus private media plus legacy `web/static/uploads/` from every actual mount. Inventory `users.avatar_key`, `posts.image_url`, `comments.image_url`, `private_messages.image_path`, and existing pending DM uploads. Do not assume frontend/backend copies match or that image builds include runtime files.
2. Install additive schema/ownership records first. Normalize known relative legacy URLs without path traversal; use deterministic unique mapping so retries cannot duplicate association or change media identity. Unreferenced legacy DM files have no reliable historical uploader: quarantine, report and retain for explicit recovery; never guess ownership or sweep them as proven garbage.
3. Copy referenced bytes to private temporary objects, validate type, sync/rename, then atomically mark manifest/association ready. Preserve source bytes during migration; crash before DB commit leaves a recoverable source plus unreachable copy. Resume pending manifest entries at startup. Never rewrite a reference to an uncopied file.
4. Missing or unmappable referenced bytes produce a recovery report identifying affected resource IDs in operational output; keep references/source, mark missing, return 404 for those image reads while retaining accessible text content. This is an explicit degraded outcome, not successful byte preservation. Storage/DB failures prevent readiness. Restore supplied missing bytes and rerun reconciliation to move missing→ready.
5. Install backend reads and frontend upload-prefix proxy interception together; raw static fallback must never serve a denied upload. Preserve unrelated static assets. Verify anonymous/outsider/follower/owner/DM participants and guessed/encoded/traversal paths before accepting privacy.
6. Expand the current avatar sweep to recognize **all** committed resource owners before enabling it against mixed objects. Account-only cleanup must never run over newly copied content/DM bytes. Delete new temporary/orphan objects only after complete ownership reconciliation; quarantine unknown legacy files. Delete an object after removal only when no retained association references it, including nested descendants/DMs/drafts.

New content writes sync private files before committing references and clean staged objects on rollback; replacements delete old objects only after commit and a complete reference check. DM upload-before-send remains compatible: record uploader/recipient and creation time durably, allow only matching authenticated sender attachment, and keep pending uploads out of unrelated orphan sweeps. B13 must specify/test pending-upload expiry before enabling destructive pending cleanup; no expiry is silently chosen by B10.

## Recovery and verification handoff

Numbered SQL migrations use existing `golang-migrate` startup; dirty/failed versions refuse service. Notification table rebuild must copy and verify before dropping old table/indexes, preserve FK references and ID allocation, and check `foreign_key_check` plus row/read-state totals on disposable upgrade fixtures. Do not auto-reset data or force dirty versions. Backups cover DB and both legacy/private media; SQL down alone cannot safely roll back an already migrated media runtime. After new follows/notices exist, restore a coordinated backup for rollback instead of dropping them silently.
